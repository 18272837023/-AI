# 技术标 AI 生成框架

> 版本 v1.0　｜　2026-10-27
> 来源：与业内从业者的访谈整理（`标书思路整理.docx`）
> 定位：这是生成链路的**设计依据**，不是提示词技巧合集。现有产品方案中与本文件冲突的部分，以本文件为准。

---

## 一、访谈里最有价值的 7 条硬事实

访谈给出的每一条都直接改变产品设计，逐条对应：

| # | 访谈原话（摘要） | 对产品的影响 |
|---|---|---|
| 1 | 「技术标没有行业固定格式规范，按照投标文件给定的技术标大纲拓展编写」 | **不做模板库**。技术标的核心动作是"服从招标文件的大纲"，不是"套我们的模板"。谁想教用户怎么写，谁就废标 |
| 2 | 大纲命名不固定：「承包人建议书」「承包人实施计划」「服务方案」 | 解析**不能按固定标题匹配**，必须按语义识别"哪一章是技术标大纲" |
| 3 | 大纲约束有三种强度（严格 / 给定但不严格 / 没给） | 产品必须区分三种模式，**这是最容易被忽略、也最容易直接导致废标的一点**（见第四章） |
| 4 | 项目类型分总承包（EPC）与单独采购，后者又分工程造价、施工类、服务咨询 | 影响章节骨架与术语体系，是"大纲生成"的第二输入 |
| 5 | 写作前重点看两处：招标公告（范围、服务期限、质量要求）、发包人要求/采购需求/技术要求（详细要求，**有时以附件形式呈现**） | 必须支持**多文件**（正文 + 附件）。现在只支持单文件，这是硬缺口 |
| 6 | 技术标内容分两类：**不依赖公司基本信息**的，和**依赖公司基本信息**的（管理制度、项目审核制度、仪器设备） | 决定哪些章节能全自动生成，哪些必须用户提供。这是"能不能少改"的关键 |
| 7 | 评分标准分两段：**基本要求（形式、资格、响应性）都满足才不废标**，之后才进入打分 | 数据模型必须拆成**合格性条款**与**得分项**两层，不能混在一个列表里 |

另外两条产品化提示：
- 「投标所需其他材料，需要补充投标响应承诺」——技术标导出时应自动生成**响应对照表**，而不是只有正文
- 「投标人放查询截图」——资质查询截图属商务标范畴，我们不做，但要在导出页明确提示用户

## 二、生成框架总览

```
Stage 0  输入归一    多文件（正文+附件）→ 文本/表格结构化 → 章节树
Stage 1  要素抽取    项目要素 / 合格性条款 / 评分细则 / 给定大纲 + 约束强度
Stage 2  大纲构建    三模式分支，评分项 → 章节映射，标注依赖等级
Stage 3  素材装配    company 章节生成结构化提问单，输出待补清单
Stage 4  分章生成    四段式骨架 + 条款响应 + 素材织入
Stage 5  三重自检    合格性覆盖 / 评分项覆盖 / 合规核验
Stage 6  装配导出    正文 + 评分响应索引表 + 要求响应对照表
```

| 阶段 | 输入 | 输出 | 典型失败模式 |
|---|---|---|---|
| 0 输入归一 | PDF/Word 正文 + 附件 | 带页码/章节号的结构化文本 | 附件漏传，技术要求整段缺失 |
| 1 要素抽取 | 结构化文本 | 四类要素 JSON | 大纲模式判错（后果：废标） |
| 2 大纲构建 | 四类要素 | 锁定/半锁定/自由大纲 | 在严格模式下擅自增删章节 |
| 3 素材装配 | 大纲 + 素材库 | 待补字段清单 | company 章节让 AI 硬编，编出假制度 |
| 4 分章生成 | 章节 + 评分细则 + 素材 | 章节正文 | 空话、编造规范号、跨章重复 |
| 5 三重自检 | 全文 | 阻断/警告/通过 | 漏响应合格性条款 |
| 6 装配导出 | 全文 + 索引 | docx + 两张对照表 | 只有正文，评委找不到分 |

## 三、Stage 1：解析要抽出四类要素

### 3.1 项目要素卡

从「招标公告」抽，不是从正文抽——访谈明确这是第一入口。

```
scope        招标范围 / 工作范围（决定技术方案覆盖哪些专业）
duration     服务期限 / 工期（决定进度计划的边界）
quality      质量要求（合格 / 优良 / 争创奖项）
location     实施地点（影响施工部署、环保、运输）
type         EPC 总承包 / 单独采购（造价 / 施工 / 服务咨询）
```

`type` 是后续大纲生成的第二输入，不能只当作标签展示。

### 3.2 合格性条款（形式 / 资格 / 响应性）

访谈把这一类单独拎出来说，因为**它不产生分数，但决定生死**。

```
形式类：格式、装订、份数、签字盖章、密封、暗标要求、页数上限
资格类：营业执照、资质等级、安许证、建造师、财务、业绩门槛
响应性：投标有效期、工期、质量标准、★实质性条款、付款方式
```

每条必须带：`类型`、`要求原文`、`出处（章节号）`、`响应方式（技术标内响应 / 需另附材料 / 不涉及技术标）`。

**只有 `响应方式 = 技术标内响应` 的才进入技术标生成与自检**，其余的在报告里提示用户去商务标处理。这一层过滤是产品边界，也是不越界的证明。

### 3.3 评分细则（只取技术部分）

```
{ 评分项, 分值, 评分档次描述, 关键词, 原文位置 }
```

关键在**评分档次描述**：多数评分表写的是"措施完善、针对性强的得 4—5 分；一般的得 2—3 分；无措施的得 0 分"。这句话就是生成标准——它告诉我们评委按什么分档，比"分值"有用得多。生成时必须把档次描述喂进提示词。

### 3.4 给定大纲 + 约束强度判定

判据（按招标文件里的措辞判定，不看章节名）：

| 措辞特征 | 判定 | 依据 |
|---|---|---|
| 「投标文件格式」「必须按本章格式编制」「不得更改章节顺序」「否则视为无效投标」 | `strict` 严格 | 改一个字都可能废标 |
| 「参照…编制」「应包括但不限于」「可结合自身情况调整」 | `guided` 半严格 | 可增章，不可减项 |
| 通篇无技术标大纲章节，只有评分标准 | `free` 自由 | 按评分标准自建 |

输出必须带**证据原文 + 页码**，让用户能核对。置信度低时不要自己决定，直接给三个选项让用户点一下——这一步点错，后面全废。

## 四、Stage 2：三种大纲模式的产品差异

这是本框架的核心。现有产品"AI 生成 8 章、可随意增删"的设计，在 `strict` 模式下是**有害的**。

| | `strict` 严格 | `guided` 半严格 | `free` 自由 |
|---|---|---|---|
| 招标文件给了大纲 | 给了，且要求照做 | 给了，但允许调整 | 没给 |
| 能否增删章节 | **禁止** | 允许新增，禁止删减 | 自由 |
| 能否改章节标题 | **禁止**（连标点都要一致） | 可微调措辞 | 自由 |
| 评分项如何映射 | 挂到已有章节下，不改骨架 | 优先挂已有，缺的补新章 | 每个评分项至少一章 |
| 违反后果 | 形式审查不通过 → 废标 | 一般不影响，可能扣印象分 | 无 |
| UI 行为 | 大纲列表**只读**，标题置灰带锁 | 可插入，新增章标注「补充章节」 | 完全可编辑 |
| 生成策略 | 只在大纲叶子节点下写内容 | 按大纲写 + 按评分标准补章 | 评分标准优先级最高 |

**产品必须做的事**：
1. 解析阶段输出 `outline_mode` + 证据，让用户确认（一键三选）
2. 大纲页根据 mode 切换为只读/半开放/全开放，`strict` 下连拖拽排序都要关掉
3. `strict` 模式下如果用户硬要加章节，提示"当前招标文件要求严格按给定大纲，新增章节可能导致形式审查不通过"，并记录在导出检查项里

## 五、Stage 3：章节依赖分级（决定"能自动到哪一步"）

访谈第六条是整个"少改"目标的钥匙。按依赖程度给每个章节打标签：

| 等级 | 含义 | 典型章节 | AI 能做什么 | 用户要做什么 |
|---|---|---|---|---|
| `auto` | 不依赖公司信息 | 项目理解、施工部署、技术措施、质量/安全保障、进度计划、应急预案 | 全自动生成 | 审阅 |
| `company` | 完全依赖公司信息 | 管理制度、项目审核制度、仪器设备清单、人员配置、企业工法 | **不写正文**，生成结构化提问单 | 填空（字段级） |
| `mixed` | 框架通用 + 局部依赖公司 | 组织机构、检测手段、类似经验 | 生成框架，公司数据留占位 | 补占位字段 |

### `company` 章节的处理方式

不给用户一个空白文档让他写，而是给**字段清单**。例如「企业管理制度」：

```
制度名称        [下拉/输入]
发布年份        [数字]
覆盖范围        [公司级 / 分公司级 / 项目部级]
审批层级        [总经理 / 管理者代表 / 部门负责人]
是否有受控版本号 [是 / 否]
```

用户填完 5 个字段，AI 织成 400 字正文。**这才是"不让用户改太多"的真实含义**：用户的动作从"写文章"降级为"填表格"。

如果用户不填，AI 不能编——编出来的"XX 公司质量管理制度（2023 版）"一旦与事实不符，评标现场一查就是虚假响应。所以 `company` 章节未填字段时，正文保留 `〔待确认：制度名称〕` 并在导出前阻断。

### 素材装配顺序

```
company 字段 → 素材库（同类型历史素材）→ 招标文件里的要求原文 → 留空占位
```

素材库里已有的（工艺标准、专项方案、设备参数），直接召回，不打扰用户；没有的才进待补清单。**待补清单要合并同类项**——10 个章节都要"设备清单"，只问一次。

## 六、Stage 4：分章生成的四段式骨架

技术标每一节的可投标标准，不是"写得好"，是"评委能照着给分"。所以按评分档次描述反推结构：

```
① 目标与标准   本节要达成什么，依据哪条规范/招标条款
② 具体措施     怎么做，分几个动作，每个动作的工艺/方法/参数
③ 资源保障     人（岗位+数量）、机（设备+台数）、料（材料+标准）、时间（频次/节点）
④ 检验与记录   谁来查、查什么、记录什么表、不合格怎么处理
```

四个硬约束（写进 system prompt，生成后逐条校验）：

1. **每个论点必须落到参数、数量、频次、岗位**，禁止出现"高度重视""切实加强""确保万无一失"
2. **必须引用招标文件条款号**（如"响应第五章 5.2.1"），这是响应性的证据
3. **禁止出现公司名、人名、Logo**（暗标场景），连"我公司"也尽量避免，用"项目部""承包人"替代
4. **不确定的数值用 `〔待确认：xxx〕` 占位**，不许编。宁可留 5 个占位，也不要写一个看起来合理但错误的数据

第 4 条是最反直觉、也最重要的一条。模型的本能是"把话说圆"，但技术标里一个编造的规范号，评审专家一眼就能看出来，代价是整章可信度崩塌。**留白比编造安全**。

## 七、Stage 5：三重自检（必须可判定、可阻断）

### 7.1 合格性覆盖检查（阻断级）

对每条 `响应方式 = 技术标内响应` 的合格性条款，检查全文是否有对应响应位置。

```
通过：有明确响应段落，且带条款号引用
警告：有相关段落但未点明条款号
阻断：全文无对应内容 → 不允许导出
```

### 7.2 评分项覆盖检查（警告级）

对每个评分细则，检查其**关键词**在对应章节的覆盖率。

```
关键词来源：评分档次描述里的名词短语（如"不停航""净空""应急撤离"）
覆盖率 ≥ 80%  通过
60%—80%       提示补写，标出缺失关键词
< 60%         警告，建议重写该节
```

### 7.3 合规核验（阻断级）

| 检查项 | 规则 | 处理 |
|---|---|---|
| 暗标词表 | 公司名、人名、Logo、电话、网址 | 命中即阻断 |
| 规范号白名单 | 所有 `GB/T xxxxx`、`JGJ xxx` 必须存在于白名单 | 不存在的编号标红，阻断 |
| 页数上限 | 按招标文件限制核算正文页数 | 超限警告 |
| 占位残留 | `〔待确认：…〕` 数量 | 存在则阻断导出 |
| 章节骨架 | `strict` 模式下比对标题与招标原文 | 不一致即阻断 |

**规范号白名单**是个容易被低估的工程：维护一份常用建筑/能源类标准目录（GB、GB/T、JGJ、DL、NB 等），生成时约束模型只能引用目录内的编号。这比事后校验更有效。

## 八、Stage 6：输出不只是正文

导出必须包含三部分，缺一不可：

**1. 技术标正文**（排版按招标文件要求：字体、字号、行距、页眉页脚、页码、暗标清理）

**2. 评分标准响应对照表**

| 评分项 | 分值 | 对应章节 | 页码 | 关键响应句 |
|---|---|---|---|---|
| 施工组织设计 | 12 | 第二章 2.1—2.3 | P12 | 采用分区流水施工，光伏区与储能区分三段推进… |

**3. 招标要求响应对照表**

| 条款号 | 要求摘要 | 响应位置 | 响应说明 |
|---|---|---|---|
| 5.2.1 | 光伏组件效率 ≥ 22.5% | 2.2.3 | 选用效率 22.8% 的 N 型组件 |

这两张表的价值：
- 评委按评分表找分，有索引表和没有，阅读体验差一个档次
- 用户自查"有没有漏项"，比通读 4 万字快得多
- 我们用它证明"覆盖了全部评分项"，这是产品可信度的来源

访谈里提到「补充投标响应承诺」，本质上就是第三张表的变形，可以合并。

## 九、用户到底要改多少

目标：**正文不改字，只填空和确认**。用户动作收敛为三类：

| 动作 | 频次 | 形态 | 耗时 |
|---|---|---|---|
| 确认大纲模式 | 1 次 | 三选一（附证据原文） | 10 秒 |
| 填 `company` 字段 | 5—10 个字段 | 表单（下拉/数字/单选） | 3—5 分钟 |
| 审阅 `〔待确认〕` | 通常 3—8 处 | 逐条跳转，填数或采纳建议 | 5—10 分钟 |

如果用户需要大段改写正文，说明前两个环节出了问题：要么大纲模式判错（写错骨架），要么 `company` 字段没收集够（AI 只能编）。

## 十、与当前 MVP 的差距（P0 改动清单）

| 现状 | 需要改成 | 影响页面 |
|---|---|---|
| 单文件上传 | 支持多文件（正文 + 附件），并标注"技术要求附件" | create |
| 解析报告 4 个 Tab，评分与风险混排 | 拆成：项目要素 / **合格性审查** / 评分细则 / 大纲（含模式与证据） | analysis |
| 大纲可自由增删 | 按 `outline_mode` 三态：只读 / 半开放 / 全开放 | outline |
| 章节无依赖标记 | 每章标 `auto` / `company` / `mixed` | outline、chapter |
| 素材库按文件类型分类 | 按「依赖公司的字段」组织，支持字段级召回 | materials |
| 导出只有正文 | 正文 + 评分响应索引表 + 要求响应对照表 | export |
| 无自检环节 | 导出前跑三重自检，阻断项列出清单 | export（新增校验页） |

## 十一、最小验证路径

先不要做全链路。拿一份真实招标文件（**含技术要求附件**），只跑：

```
Stage 1 全量抽取  →  Stage 2 大纲构建  →  一个 company 章节 + 一个 auto 章节
```

看三件事，任何一件不达标，后面都不用做：

1. **大纲模式判定对不对**（拿招标原文人工核对，错了就是废标风险）
2. **合格性条款抓没抓全**（对照招标文件"投标人须知前附表"逐条比）
3. **company 字段够不够填**（让真实投标人试着填一遍，看他卡在哪）

这三件事的验证成本很低（几毛钱 API + 半小时人工核对），但能决定整个产品是否成立。
