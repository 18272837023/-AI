# 服务端能力层设计（质量保证的工程载体）

> 版本 v1.0　｜　2026-10-30
> 前置阅读：`技术标生成框架.md`（链路）、`质量控制设计.md`（质量标准）
> 本文件回答一个问题：**质量靠什么在工程上被保证，而不是靠提示词碰运气。**

---

## 零、先澄清 Skill 的两种含义

| | WorkBuddy Skill | 服务端能力单元 |
|---|---|---|
| 形态 | `SKILL.md` + 脚本，agent 读取后执行 | 部署在服务器上的函数/服务，有明确 I/O schema |
| 运行环境 | agent 会话 | 生产服务器，面向全部用户 |
| 是否可测 | 靠人读、靠试 | 单元测试 + 基准集回归 |
| 适合做什么 | 固化方法论、团队协作规范、开发期辅助 | **产品运行时** |

**结论：产品运行时不用 Skill，用能力单元。** Skill 的价值在开发期（见第七章），不在生产环境。

理由很直接：Skill 是"给模型看的说明书"，行为不确定、不可断言、成本不可控。而技术标的质量要求是**可判定**的——可判定的东西就该用确定性代码实现。

---

## 一、总览：6 层 24 个能力单元

```
L0 输入归一    M01 文档归一化  M02 章节树构建  M03 附件关联
L1 要素抽取    M04 项目要素    M05 合格性条款  M06 评分细则
               M07 大纲识别    M08 技术条款
L2 结构构建    M09 施工图 ★    M10 依赖分级    M11 大纲构建  M12 素材装配
L3 内容生成    M13 要素表 ★    M14 正文展开    M15 约束注入  M16 占位符管理
L4 校验修复    M17 合格性覆盖  M18 要素覆盖    M19 合规核验  M20 文风检测
               M21 语义判定    M22 修复执行
L5 装配输出    M23 排版渲染    M24 索引表      M25 留痕版本
横切           M26 指标计算    M27 基准回归    M28 成本配额
```

★ 标记的是决定质量的两个核心单元。

## 二、L0 输入归一

| 编号 | 名称 | 职责 | 实现 | 失败策略 |
|---|---|---|---|---|
| M01 | 文档归一化器 | PDF/DOCX/扫描件 → 带页码坐标的结构化文本 | 规则 + OCR | **阻断**（无文本则无后续） |
| M02 | 章节树构建器 | 识别标题层级、表格、正文边界 → 章节树 | 规则为主 | 降级为平铺 + 警告 |
| M03 | 附件关联器 | 识别"技术要求/发包人要求"附件并与主文件关联 | LLM + 规则 | **警告并阻断生成**（附件缺失=技术要求整段缺失） |

M01 的硬要求：**保留页码和章节号**。没有坐标，后面所有"原文出处"都是假的。

M03 是访谈直接带出的缺口：技术要求常以附件形式给出，漏传则方案全错。这一层必须显式提示，不能静默通过。

## 三、L1 要素抽取（四类要素 + 一个判定）

| 编号 | 名称 | 输出 | 实现 | 失败策略 |
|---|---|---|---|---|
| M04 | 项目要素抽取器 | scope / duration / quality / location / type | LLM + JSON Schema | 阻断（缺 type 无法建大纲） |
| M05 | 合格性条款抽取器 | 形式/资格/响应性条款 + **响应方式判定** | LLM + 规则校验 | 阻断（漏一条=废标） |
| M06 | 评分细则抽取器 | 评分项 / 分值 / 档次描述 / 关键词 / 出处 | LLM + 规则校验 | 阻断（分值合计≠技术标总分则重试） |
| M07 | 大纲识别与模式判定器 | outline_mode + 证据原文 + 置信度 | LLM + 规则 | 低置信度→强制用户三选一 |
| M08 | 技术条款抽取器 | ★实质性条款 / 技术指标 / 格式规则 | LLM | 阻断（★条款漏抽=负偏离） |

### 3.1 这一层的三个工程约束

**约束一：JSON Schema 强制**。所有抽取结果必须过 schema 校验，失败重试最多 2 次，仍失败则返回结构化错误，不返回半成品。

**约束二：交叉校验**（规则层，不用模型）
- 评分项分值合计 == 技术标总分，不等则告警并要求人工确认
- 合格性条款数量 == 招标文件"投标人须知前附表"条目数（±2 容差）
- ★条款编号连续性与原文一致

**约束三：每条结果必带 evidence**（章节号 + 页码 + 原文片段）。没有 evidence 的抽取结果视为无效——这是用户能核对的前提，也是我们的免责依据。

### 3.2 M05 的响应方式判定（产品边界的关键）

```
技术标内响应  → 进入生成与自检
需另附材料    → 报告提示，不进技术标
不涉及技术标  → 直接过滤
```

这一层过滤是"只做技术标"承诺的工程落地。判错的后果：把商务要求写进技术标（越界）或漏掉技术响应（废标）。

## 四、L2 结构构建

| 编号 | 名称 | 职责 | 实现 | 失败策略 |
|---|---|---|---|---|
| M09 | **施工图生成器** | 评分项 → 必答要素清单（4—7 条/项） | LLM + 规则收敛 | 阻断（无施工图不生成） |
| M10 | 依赖分级器 | 每章标 auto / company / mixed | LLM + 关键词规则 | 降级为 mixed（保守） |
| M11 | 大纲构建器 | 三模式分支：严格照抄 / 增补 / 自建 | 规则为主 | 阻断 |
| M12 | 素材装配器 | 字段级召回 + 待补清单合并 + 脱敏闸门 | 规则 + 向量检索 | 降级为空素材 + 待补 |

### 4.1 M09 是整条链的标准源

施工图输出结构（与 `质量控制设计.md` 第三章一致）：

```
score_item / score / tier_desc / keywords[] / elements[] / source
elements[i] = { id, name, must_have }
```

**下游所有单元只引用施工图，不允许各自重新理解评分标准。** 这是"单一事实源"原则——否则生成按 A 理解、自检按 B 理解，算出来的覆盖率是假的。

要素收敛规则（规则层，非模型）：
- 要素数 < 4 → 要求补充（拆太粗，缺项风险高）
- 要素数 > 7 → 合并同义项（拆太细，用户无法判断）
- 每条 `must_have` 必须包含"名词+可验证量"，纯形容词打回重拆

### 4.2 M12 的脱敏闸门（硬性）

素材入模前必须过脱敏：
- 页眉页脚剥离
- 公司名/项目名替换为"承包人""本工程"
- 人名、电话、网址、Logo 位置标记

**这一步不能放到导出时做**——导出清得掉页眉，清不掉已经写进句子的"我公司"。素材污染正文是暗标废标高发点。

## 五、L3 内容生成

| 编号 | 名称 | 职责 | 实现 | 失败策略 |
|---|---|---|---|---|
| M13 | **要素表生成器** | 要素 → 要素表（做法/参数/岗位/频次/置信度） | LLM（强约束） | 重试；失败则降级为占位 |
| M14 | 正文展开器 | 要素表 → 正文（只组织文字，不新增事实） | LLM | 重试；失败标失败章 |
| M15 | 约束注入器 | 规范号白名单、术语表、四段式骨架注入 | **纯规则** | 不失败 |
| M16 | 占位符管理器 | 生成 `〔待确认：xxx〕`、统一编号、追踪清零 | **纯规则** | 不失败 |

### 5.1 M13 → M14 两段式的工程含义

```
M13 输出：结构化要素表（可校验、可展示、可编辑）
    ↓ 用户确认 / 规则补全
M14 输出：正文（纯文字组织）
```

关键：**M14 的输入里只有已确认的要素表，没有原始评分细则**。物理上杜绝"展开时重新发挥"。这是用架构而非提示词来保证"不编造"。

### 5.2 M16 占位符是产品资产，不是缺陷

```
〔待确认：现场临时用电容量〕
〔待确认：企业质量管理制度名称与版本号〕
```

统一格式 + 唯一编号，带来的能力：
- 导出前可精确统计与阻断
- 用户逐条跳转填写，填完自动替换
- 素材库积累后，同类占位自动预填（第二次用同一家企业就不用再填）

**占位符数量本身是质量指标**：太多说明素材不足，太少要怀疑是不是编了。

## 六、L4 校验修复（90% 是规则，这是质量地基）

| 编号 | 名称 | 职责 | 实现 | 级别 |
|---|---|---|---|---|
| M17 | 合格性覆盖检查器 | 条款号锚点 + 段落引用匹配 | **纯规则** | 阻断 |
| M18 | 要素覆盖检查器 | 施工图要素 vs 正文段落标记，结构比对 | **纯规则** | 阻断 |
| M19 | 合规核验器 | 暗标词表 / 规范号白名单 / 页数 / 骨架比对 | **纯规则** | 阻断 |
| M20 | 文风检测器 | 参数密度、空话词表、句长分布 | **纯规则** | 警告 |
| M21 | 语义判定器 | "这段是否真的回应了这条要求" | LLM（抽样） | 警告 |
| M22 | 修复执行器 | 问题 → 定位 → 一键动作映射 | 规则 + 局部 LLM | — |

### 6.1 为什么校验层几乎不能有模型

**校验结果必须是确定的。** 如果自检本身用模型，同一个稿子两次跑出不同结论，用户就无法依赖这个"通过"——那这个功能就是装饰品。

M21 是唯一例外，且限定用途：
- 只对 M18 判定"结构上已覆盖但语义可疑"的段落做抽样复核
- 单次调用，温度 0，输出只有 pass / fail / unclear
- 结果只产生警告，不产生阻断

### 6.2 M22 是"报告"和"产品"的分界线

竞品的审查功能输出一份 PDF 清单，用户自己去找、自己改。M22 必须做到：

```
问题 → 章节ID → 段落ID → 句子偏移 → 动作
动作类型：补写要素 / 替换表述 / 降级为占位 / 跳转人工
```

没有 M22，前面五个检查器都只是"看起来很专业"。

### 6.3 阻断清单

```
导出按钮可用条件：
  M17 阻断项 = 0
  M18 未覆盖要素 = 0
  M19 阻断项 = 0
  M16 占位残留 = 0
```

这个门禁强硬，但它是产品唯一能对"不废标"负责的方式。

## 七、L5 装配输出 + 横切

| 编号 | 名称 | 职责 | 实现 |
|---|---|---|---|
| M23 | 排版渲染器 | docx 生成，按招标格式（字体/字号/行距/页眉/页码/暗标清理） | 模板引擎 |
| M24 | 索引表生成器 | 评分响应表 + 要求响应对照表（含页码回填） | 规则 |
| M25 | 留痕版本器 | 记录模型、提示词版本、token、耗时、素材引用 | 规则 |
| M26 | 指标计算器 | 六项质量指标（见质量控制设计第六章） | 规则 |
| M27 | 基准回归器 | 5 份真实招标文件跑基准集，输出指标对比 | 规则 |
| M28 | 成本配额器 | token 计量、限流、异常熔断 | 规则 |

M24 的页码回填依赖 M23 的渲染结果——所以必须先渲染再生成索引，顺序不能反。

M25 有两个用途：出问题能追溯是哪版提示词导致的；给用户看"这份稿子引用了你素材库的哪 3 份文件"，建立信任。

## 八、三条贯穿全层的架构原则

### 原则一：契约化（上游错误不静默传递）

每个单元有显式 I/O schema，跨单元传递时强制校验。schema 变更导致下游编译/校验失败，而不是运行时算出错误结果。

**收益**：改一个抽取字段，立刻知道影响哪几个下游，而不是上线后才发现覆盖率算错。

### 原则二：不确定性必须传播

每个 LLM 单元输出必带：

```
confidence: high | medium | low
evidence: { section, page, quote }
```

下游按 confidence 决定行为：

| confidence | 下游行为 |
|---|---|
| high | 自动通过 |
| medium | 保留但标记，进入用户确认清单 |
| low | **不自动决定**，强制用户选择 |

典型应用：M07 大纲模式判定 low → 不自动设 strict/guided/free，直接给用户三个选项 + 证据原文。这一步点错，四万字全废。

**这是"不假装确定"的工程表达**，也是产品可信度的来源。

### 原则三：单一事实源

```
施工图(M09)  →  要素表(M13)  →  正文(M14)  →  校验(M18)
     ↑ 唯一标准，下游只引用不重解
```

禁止任何单元自行理解评分标准。否则覆盖率、自检、导出索引三处口径不一致，用户一核对就露馅。

## 九、开发期 Skill 清单（这才是 Skill 该出现的地方）

产品运行时不用 Skill，但**开发与运营期应该用**，把方法论固化成团队可复用的资产：

| Skill | 作用 | 使用者 |
|---|---|---|
| `tender-parse-spec` | 解析阶段的抽取规范：四类要素字段定义、evidence 要求、交叉校验规则 | 后端开发、评测 |
| `element-breakdown` | 评分项拆要素的方法：名词短语识别、四段式维度、4—7 条收敛规则 | 提示词工程、产品 |
| `outline-mode-judge` | 大纲三态判据：措辞特征表、证据要求、低置信度处理 | 提示词工程 |
| `compliance-rules` | 暗标词表、规范号白名单维护规范、页数核算口径 | 运营、法务 |
| `quality-benchmark` | 基准集跑法：5 份样本、六指标计算、结果判定 | 评测、迭代 |
| `prompt-registry` | 提示词版本管理规范：变更记录、回归要求、灰度策略 | 后端开发 |

这些 Skill 的共同点：**它们是给人用的说明书，不是给生产环境调用的函数**。混用会导致架构腐化。

## 十、分期落地（按质量杠杆排序）

| 期 | 单元 | 判断标准 |
|---|---|---|
| P0 | M01 M02 M05 M06 M07 M09 M13 M14 M16 M17 M18 M19 | 拿真实招标文件跑通，六指标可测 |
| P1 | M03 M04 M08 M10 M11 M12 M15 M20 M22 M23 M24 | 端到端可导出，用户只需填空 |
| P2 | M21 M25 M26 M27 M28 | 可迭代、可追溯、可控成本 |

**P0 的最小闭环**：解析 → 施工图 → 要素表 → 正文 → 规则自检。

这套闭环做完，就能回答那个关键问题：**AI 拆出来的要素，够不够内行用。** 不够，后面全是白做；够，再往上加。

---

## 十一、一句话总结

> 质量不来自更聪明的模型，来自**可判定的标准（施工图）+ 可校验的中间态（要素表）+ 不可绕过的门禁（规则自检）+ 会传播的不确定性（confidence）**。

模型只负责两件事：把招标文件读懂，把要素表写成通顺的中文。其余全部交给确定性代码。
