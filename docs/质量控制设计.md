# 技术标生成的质量控制设计

> 版本 v1.0　｜　2026-10-30
> 前置阅读：`技术标生成框架.md`（讲链路）、本文件（讲质量如何被保证）
> 核心判断：**技术标是证明题，不是作文。质量不来自文笔，来自结构与覆盖。**

---

## 一、质量的可判定定义

访谈给出三层判据，从下往上任何一层不达标，上一层归零：

| 层级 | 判据 | 由谁判定 | 不达标的后果 |
|---|---|---|---|
| L1 不废标 | 形式 / 资格 / 响应性条款全部满足 | 形式审查（机器可查） | 0 分，出局 |
| L2 拿到应得分 | 每个评分项的档次描述被正面回应 | 评委（对照评分表） | 应得 45 分实得 20 分 |
| L3 评委找得到 | 响应对照表可用，条款号与页码对得上 | 评委（阅读体验） | 默认按低档给分 |

**产品内部不设"文笔分"。** 任何无法落到 L1—L3 的优化都不做。

---

## 二、四类失败模式与责任归属

| 失败模式 | 表现 | 根因 | 解法 | 能否靠换模型解决 |
|---|---|---|---|---|
| 骨架错 | 严格模式下擅自增删章节 | 流程 | 大纲三态 + 用户确认 | ❌ |
| 缺项 | 漏响应★条款 / 评分项无对应章节 | 流程 | 施工图 + 覆盖矩阵 | ❌ |
| 编造 | 不存在的规范号、假的制度版本 | 约束缺失 | 白名单 + 占位符 | ❌ |
| 空话 | "高度重视""切实加强" | **模型能力** | 要素表 + 参数密度 | ✅ 部分 |

结论：**四类里三类是流程问题。** 质量保证靠结构，不靠模型选型。

---

## 三、前置闸门：评分表 → 施工图

### 3.1 为什么需要这一步

招标文件的评分表通常长这样：

```
绿色施工与零碳专项方案    8 分
措施完善、针对性强、可操作性好的得 7—8 分；
措施基本可行、针对性一般的得 4—6 分；无相关措施的得 0 分。
```

这段话对人是标准，对模型是废话——"完善""针对性强"无法直接执行。必须翻译成**必答要素清单**：

```json
{
  "score_item": "绿色施工与零碳专项方案",
  "score": 8,
  "tier_desc": "措施完善、针对性强、可操作性好的得 7—8 分",
  "keywords": ["零碳", "碳排因子", "光伏消纳", "储能配置", "净空", "不停航"],
  "elements": [
    { "id": "E1", "name": "碳排基线测算", "must_have": "测算方法 + 排放因子来源 + 基线数值" },
    { "id": "E2", "name": "光伏与储能容量配置", "must_have": "装机容量 + 消纳比例 + 并网方式" },
    { "id": "E3", "name": "施工期减排措施", "must_have": "分项措施 + 单项减排量估算" },
    { "id": "E4", "name": "计量与监测", "must_have": "计量点位 + 采集频次 + 仪表精度" },
    { "id": "E5", "name": "偏差处置", "must_have": "预警阈值 + 处置流程 + 责任岗位" }
  ],
  "source": "第五章 5.4.2"
}
```

### 3.2 这份清单是唯一的质量标准载体

- **生成**时逐条写，写不出的留占位
- **自检**时逐条查，缺一条就是缺一项分
- **UI** 上就是 5 个可勾选的框，用户一眼看出还差什么

**要素清单的拆法**（不依赖行业知识，可稳定复现）：

1. 档次描述里的每个名词短语 → 一个候选要素
2. 加上四段式骨架的固定维度：目标 / 措施 / 资源 / 检验
3. 合并同义项，控制在 4—7 条（超过 7 条说明拆得太细，用户无法判断）

### 3.3 缺项的机器判定

```
覆盖率 = 已响应要素数 / 要素总数
L2 达标线：每个评分项覆盖率 = 100%（不是 80%）
```

之所以要求 100%，是因为**评分是分档的，缺一条要素就可能从"完善"掉到"一般"，直接掉一档**。掉一档是 3—4 分，不是 0.5 分。

## 四、中置闸门：要素表 → 展开（最核心的设计）

### 4.1 不让模型直接写正文

**错误做法**：给模型评分细则 + 素材，让它输出 4000 字。
**正确做法**：两段式。

**第一段 —— 出要素表**（JSON，短，可控）

```json
{
  "section": "2.3 绿色施工与零碳专项方案",
  "rows": [
    {
      "element": "E1",
      "point": "以 2023 年为基准年，按《建筑节能与可再生能源利用通用规范》GB 55015 核算施工期碳排放",
      "params": ["基准年 2023", "核算边界：施工+运输", "排放因子来源：省级电网平均因子"],
      "owner": "项目技术负责人",
      "freq": "开工前一次，季度复核",
      "confidence": "high",
      "needs_user": false
    },
    {
      "element": "E3",
      "point": "塔吊与施工电梯改为市电驱动，减少柴油发电机使用",
      "params": ["〔待确认：现场临时用电容量〕"],
      "owner": "机电负责人",
      "freq": "全过程",
      "confidence": "medium",
      "needs_user": true
    }
  ]
}
```

**第二段 —— 按要素表展开成文**，只做文字组织，不新增事实。

### 4.2 为什么这个设计决定质量

| 维度 | 直接写正文 | 要素表 → 展开 |
|---|---|---|
| 纠错成本 | 重写 4000 字 | 改一行 |
| 用户能否判断 | 要读完全文 | 扫 5 行就知道对不对 |
| 空话检测 | 事后扫词 | 结构上不可能——每行必须带 params |
| 编造检测 | 事后查白名单 | 出表时就能标 `confidence` |
| 覆盖率计算 | 语义匹配，不准 | 数行数，精确 |

**人机分工线的正确位置**：

> AI 负责**想到**（这个项目该做哪些措施），人负责**判断对不对**（我们现场能不能这么干），AI 负责**写出来**。

用户是内行，看要素表的速度是看正文的 10 倍。让他判断"这个措施在我们机场项目上行不通"，比让他改一段不通顺的文字高效得多。

### 4.3 三档置信度与对应 UI

| confidence | 含义 | UI 表现 |
|---|---|---|
| `high` | 通用做法，有规范支撑 | 默认折叠，不打扰 |
| `medium` | 需要项目参数才能定 | 展开，字段可编辑 |
| `low` | 依赖公司或现场信息 | 标黄，进待补清单 |

`needs_user = true` 的行自动汇入待补清单，**同类字段合并**（10 个章节都要"设备清单"只问一次）。

### 4.4 展开阶段的四条硬约束

写进 system prompt，生成后逐条校验：

1. 每个论点必须落到**参数、数量、频次、岗位**，禁止"高度重视/切实加强/确保万无一失"
2. 必须引用招标文件条款号（"响应第五章 5.2.1"）
3. 禁止公司名、人名、Logo，用"项目部""承包人"替代（暗标）
4. 不确定的数值用 `〔待确认：xxx〕`，**不许编**

第 4 条是产品信誉的底线。留 5 个占位是专业，编 1 个假数据是事故。

## 五、后置闸门：自检必须闭环到修复

### 5.1 只报告不修复 = 没做

行业里常见的"标书审查"是给一份 PDF 报告，用户还得自己找、自己改。这不是产品，是作业。

我们的自检必须做到三件事：

```
定位：问题 → 章节 → 段落 → 具体句子（可跳转）
归因：属于哪条要素 / 哪条合格性条款
动作：一键补写 / 一键替换 / 一键降级为占位
```

### 5.2 检查项与处理级别

| 检查项 | 规则 | 级别 |
|---|---|---|
| 合格性覆盖 | 每条"技术标内响应"条款有对应段落且带条款号 | **阻断** |
| 要素覆盖 | 每个评分项要素覆盖率 = 100% | **阻断**（低于 100% 不许导出） |
| 暗标词表 | 公司名、人名、电话、网址、Logo | **阻断** |
| 规范号白名单 | 所有 GB/JGJ/DL/NB 编号必须在白名单内 | **阻断** |
| 占位残留 | `〔待确认：…〕` 未清零 | **阻断** |
| 章节骨架 | strict 模式比对标题与招标原文 | **阻断** |
| 参数密度 | 每千字含数值+单位的句子数 < 8 | 警告 |
| 空话词 | "高度重视"等词表命中 | 警告 |
| 页数上限 | 核算正文页数 | 警告 |

**阻断项不清零，导出按钮置灰。** 这条规则看着强硬，但它是产品唯一能对"不废标"负责的方式。

### 5.3 自检的工程实现

能用规则引擎的，不要用大模型：

- 暗标词表、规范号白名单、占位符、页数 → **纯规则**，0 成本、100% 准确
- 要素覆盖 → 结构比对（要素表 vs 正文段落标记），**不用语义匹配**
- 合格性覆盖 → 条款号正则 + 段落锚点
- 参数密度 → 正则统计

只有"这段是否真的回应了这条要求"需要模型判断，且只在这一步用，用便宜的 Flash 即可。

## 六、质量必须可度量（否则无法迭代）

### 6.1 六个指标，构成回归测试集

准备 5 份真实招标文件作为基准，每次改提示词/换模型都跑一遍：

| 指标 | 计算方式 | 目标 |
|---|---|---|
| 合格性覆盖率 | 已响应条款 / 应响应条款 | 100% |
| 要素覆盖率 | 已写要素 / 施工图要素 | ≥ 98% |
| 参数密度 | 含数值+单位的句子 / 千字 | ≥ 12 |
| 空话命中 | 空话词表命中次数 / 千字 | ≤ 2 |
| 编造率 | 白名单外规范号引用数 | 0 |
| 占位数 | `〔待确认〕` 个数 | ≤ 8（且必须都是真需人工的） |

### 6.2 为什么这套指标比"看起来不错"重要

换模型、改提示词、调参数，如果没有这六个数字，所有决策都是凭感觉。有了它，任何改动都能回答"变好了还是变坏了"。

**这也是评估"Flash 够不够"的唯一客观方式**——不是问它写得好不好，是跑一遍看六个数字。

## 七、产品交互必须改的三处

| 页面 | 现在 | 要改成 |
|---|---|---|
| 大纲页 | 只有章节名和字数 | 每章显示**要素完成度**（如 3/5），点击展开要素清单 |
| 生成前 | 直接开始生成 | 新增**要素表确认页**：5—10 行要点，用户扫一眼、改错的、确认 |
| 章节页 | AI 工具条：续写/扩写/润色 | 改为：**补要素 / 加参数 / 按评分档次提升 / 降级为占位** |

第三处改动最能体现产品差异：**"润色"是作文思维，"补要素"是证明题思维。** 竞品都在做前者。

## 八、能力边界与承诺口径

### 8.1 Flash 能到哪、到不了哪

| 能做 | 做不到 |
|---|---|
| 结构完整、要素齐全 | 现场经验判断（"夜间 2 小时窗口只能干这些活"） |
| 有参数、有岗位、有频次 | 项目特有的工艺取舍 |
| 合规、无编造、无暗标信息 | 专家级的方案比选论证 |
| 文字通顺、术语正确 | 与评委偏好匹配的"亮点包装" |

### 8.2 产品承诺应该怎么说

| ❌ 不要说 | ✅ 应该说 |
|---|---|
| "AI 一键生成技术标" | "AI 生成合规、完整、有参数的技术标初稿" |
| "专家级方案" | "覆盖全部评分项，结构可直接提交" |
| "不用改就能投" | "正文不用改字，只需填 5—10 个字段、确认 3—8 处占位" |
| "中标率提升 X%" | （违规表述，禁止出现） |

**诚实的产品承诺反而是壁垒**：用户被"一键生成"骗过一次之后，会格外信任敢说"你需要填 8 个字段"的产品。

## 九、落地顺序

不要一次做完。按质量杠杆从大到小：

1. **施工图生成**（Stage 1 增强）——没有它，后面所有覆盖率都无从计算
2. **要素表两段式生成**（Stage 4 改造）——质量提升最明显的一步
3. **规则引擎自检**（Stage 5）——纯工程，无模型风险，见效快
4. **要素表确认页**（UI）——让用户看见质量，建立信任
5. **六个指标跑基准集**——此时才有资格评估模型选型

前 3 项做完，用一份真实招标文件跑通，就能判断这个产品是否成立。
