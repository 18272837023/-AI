# AI 技术标小程序 · MVP 产品方案

> 版本 v1.1　｜　2026-10-27（收窄至技术标）　｜　配套源码：`miniprogram/`

---

## 一、产品定位

**一句话**：投标人在手机上，把一份招标文件变成一份对标评分细则的技术标初稿。

- **目标用户**：中小施工/服务企业的投标专员、项目经理（一人身兼多职，没有专职标书团队）
- **核心场景**：出差途中、开标前夜、临时接到投标任务，用碎片时间推进技术标
- **只做技术标**：施工组织设计 / 技术方案 / 服务方案这一册的解析、撰写、编辑、排版、导出
- **不做的事**：不做商务标、资格文件、投标报价与开标一览表，不做资质业绩材料代整理，不做标书代审，不做全流程招投标管理平台、造价清单、电子签章

**为什么收窄**：投标文件里只有技术标是"内容型"工作——需要写几万字方案、要逐条响应评分细则，最耗人。商务标和资格文件本质是"填空 + 贴扫描件"，标准化程度高、替代品多，做进来只会让产品变重、让用户觉得"什么都能做但什么都不精"。

**价值主张**：不是"帮你写字"，而是"帮你少废标、少漏分"。所以解析报告里的**技术标风险清单**和**评分对照**，比正文更重要。

---

## 二、核心流程与状态机

```
上传文件 → 解析中 → 解析完成 → 大纲确认 → 生成中 → 编辑中 → 已导出
             ↓失败                ↓              ↓失败
           解析失败            待确认          部分章节失败（可重试）
```

项目状态（`project.status`）：
`uploading` → `parsing` → `parsed` → `outlining` → `generating` → `editing` → `exported`，异常态 `failed`

每个章节（`chapter.status`）：
`pending` → `generating` → `done` / `failed`

## 三、功能边界

### P0（本期已搭好前端）
上传、解析、**技术标评分细则**、**技术标风险提示**、目录、分章生成、编辑、排版导出、项目管理、技术素材库（占位）

### P1（第二期）
- 技术素材库 RAG（企业工艺标准、专项方案、设备参数参与生成）
- 历史技术标复用（同类型项目调取旧稿章节）
- 暗标自检（公司名、Logo、文档属性、隐藏文字）
- 多人协作（分享给同事补充章节）
- 分享解析报告（生成图片卡片，社交裂变）

### P2（第三期）
- 技术标查重（与历史投标文件比对相似度）
- 述标 PPT / 讲稿生成（基于已生成的技术标）
- 图表自动生成（进度横道图、施工平面图、组织机构图）

> 已明确移出范围：标书审查（全文件代审）、模板库、商务标智能填空、报价策略。这些能力要么依赖商务信息，要么与"只做技术标"的定位冲突。

`parsed_json` 结构（只保留技术标所需字段）：

> 2026-10-27 修订：按业内访谈拆出「合格性条款 / 评分细则」两层，并新增大纲约束强度 `outline_mode`。详见 `docs/技术标生成框架.md`。

```json
{
  "basic": { "name": "", "purchaser": "", "budget": 0, "duration": "", "scope": "", "quality": "", "location": "" },
  "project_type": "epc | cost | construction | service",
  "tech_demands": ["技术标须响应的要求，含 ★ 实质性条款"],
  "pass_fail": [
    { "kind": "form | qualification | responsiveness", "requirement": "", "source": "第二章 4.1.6", "response_in": "tech | business | none" }
  ],
  "scores": [{ "name": "施工组织设计", "score": 12, "criteria": "措施完善、针对性强的得 4—5 分…", "keywords": ["不停航", "净空"], "source": "第三章 3.2" }],
  "score_split": { "tech": 45, "business": 25, "price": 30 },
  "outline_mode": "strict | guided | free",
  "outline_evidence": "「投标文件格式」章节要求不得更改章节顺序（P48）",
  "risks": [{ "level": "high", "title": "", "desc": "", "source": "第二章 2.3.4" }],
  "format_rules": { "blind": true, "page_limit": 300, "font": "宋体小四" }
}
```

- `pass_fail` 与 `scores` 必须分开：前者不产生分数但决定是否废标，后者才参与打分
- `response_in` 用于边界过滤：只有 `tech` 的条款进入技术标生成与自检，`business` 的提示用户去商务标处理
- `outline_mode` 判错会直接导致废标，必须带证据原文让用户确认

> `score_split` 只用于告诉用户"总分怎么分"，商务与报价的分值不参与生成。

## 五、接口设计（草案）

统一前缀 `/api/v1`，鉴权用微信 `code2session` 换取的 token。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/login` | code 换 token |
| POST | `/files/upload` | 获取云存储直传凭证 |
| POST | `/projects` | 创建项目（传 file_id、类型、模式） |
| GET | `/projects` | 项目列表（分页、状态筛选） |
| GET | `/projects/:id` | 项目详情（含 parsed_json） |
| POST | `/projects/:id/parse` | 触发解析，返回 task_id |
| GET | `/tasks/:id` | 轮询任务进度（也可用 SSE） |
| POST | `/projects/:id/outline` | 提交/更新大纲，触发目录生成 |
| POST | `/projects/:id/generate` | 触发全文生成（可指定章节） |
| GET | `/projects/:id/chapters` | 章节列表 + 状态 |
| GET | `/chapters/:id` | 章节详情 |
| PUT | `/chapters/:id` | 保存正文（自动保存） |
| POST | `/chapters/:id/ai` | 单章 AI 操作（continue/expand/polish/chart） |
| POST | `/projects/:id/export` | 生成 docx，返回下载链接 |
| POST | `/orders` | 创建支付订单 |
| POST | `/pay/notify` | 微信支付回调 |

**异步任务建议**：解析与生成都是长任务，统一用「task_id + 轮询（3s）」或 SSE。小程序对 SSE 支持一般，轮询更稳。

## 六、AI 生成逻辑（重点）

> 本章是概览。完整框架（六阶段流水线、三种大纲模式、章节依赖分级、三重自检、导出索引表）见 **`docs/技术标生成框架.md`**，该文件基于业内访谈编写，冲突时以它为准。

这是整个产品的核心，分四层。

### 第 1 层：文档解析

```
PDF / Word（扫描版 PDF 走 OCR）
  → 文本抽取（PDF 用 pdfplumber/PyMuPDF）
  → 版面还原（区分标题/正文/表格，表格单独结构化）
  → 分段切片（按章节标题切，单段 ≤ 2000 字，带页码元信息）
```

**关键**：保留**页码和章节号**，因为风险提示要能回指原文（"来源：第二章 2.3.4"），这是专业感的来源。

> 不做拍照上传：招标文件通常由采购方以 PDF/Word 发布，拍照 OCR 的识别错误率反而会污染解析结果。

### 第 2 层：结构化抽取

不要一次性让模型读完 200 页。按章节分别抽取，再合并：

- 项目基本信息：从「招标公告」「投标人须知前附表」抽
- **技术标评分细则**：从「评标办法」抽技术部分，要求模型输出 `{评分项, 分值, 评分细则, 原文位置}`；商务分与价格分只取总分，不展开
- **技术标废标/扣分条款**：从「评标办法」「技术要求」抽，只保留会导致技术标不得分/废标的条款，输出 `{风险描述, 触发条件, 原文位置, 等级}`
- **★ 实质性条款**：单独标记，生成时必须逐条明确响应，这是负偏离的高发点

用 JSON Schema 约束输出（function calling / response_format），失败重试 + 校验（技术分项分值总和必须等于技术标总分，否则告警）。

### 第 3 层：目录生成

**不是让模型自由发挥，而是技术标评分细则驱动**：

1. 每个评分项映射为至少一个章节（12 分的施工组织设计 → 一个大章 + 若干小节）
2. 字数分配算法：`章节字数 = 总字数 × (章节分值 / 技术标总分) × 系数`，核心章节系数 1.2
3. 结合项目类型插入行业必备章节（工程类：安全文明施工、进度计划；服务类：人员配置、应急预案）
4. 输出后做**覆盖度自检**：技术标每个评分项是否都有对应章节，缺失则补

### 第 4 层：分章生成

单章生成时，上下文 = 招标文件相关片段（RAG 召回）+ 项目基本信息 + 评分细则 + 已生成的前后章摘要。

```
System: 你是资深投标文件编制专家，熟悉《招标投标法》与评标规则。
        输出要求：正式书面语、不使用第一人称"我们"、不出现公司名称（暗标）、
        每个论点必须有具体措施/参数/责任人，禁止空话。
User:   【项目】{basic}
        【本章评分要求】{score.criteria}
        【招标文件相关条款】{retrieved_chunks}
        【前章摘要】{prev_summary}
        【技术素材】{materials}
        请撰写《{chapter.title}》，目标 {target_words} 字，二级标题不少于 {n} 个。
```

**长文策略**：单次生成 1500—2000 字，按小节循环续写，每轮把"已写内容摘要 + 当前小节标题"作为上下文，避免跑题和重复。

**质量兜底**：
- 生成后扫描是否出现公司名/人名（暗标场景）
- 检查是否覆盖该章评分细则的关键词
- 字数不足自动扩写，超出自动压缩

### 附：技术标需要哪些企业信息（素材库的边界）

技术标**需要企业能力，不需要企业身份**。这是最容易搞混的地方，也是暗标废标的高发点。分三类：

| 类型 | 具体内容 | 技术标里要不要 | 处理方式 |
|---|---|---|---|
| **身份型** | 公司名称、Logo、资质证书扫描件、法定代表人、联系方式、页眉页脚 | ❌ **暗标下必须隐藏**，正文出现即废标 | 入模前脱敏；导出时清除文档属性与图片 EXIF |
| **能力型** | 施工工艺标准、专项方案、设备清单与参数、检测手段、质量/安全体系文件、专利与工法、QC 成果 | ✅ **必须提供**，决定"写得像不像内行" | 素材库 RAG，按章节相关性召回 |
| **业绩型** | 类似工程经验、合同额、业主评价 | ⚠️ **看评分归属** | 多数项目放在商务资信评，不进技术标；若评分细则把"施工经验"放在技术标，才引用，且只写"某类项目 2 项"不写业主名 |

**人员信息要单独说**：技术标里的「项目管理机构」章节通常有分值（本项目 4 分），需要的是**岗位结构 + 职称 + 证书类别 + 类似项目经历**（如"项目经理：机电工程一级建造师，主持过 2 个 2000 万以上能源站项目"），**不需要姓名**。暗标场景下写姓名同样可能被判定为身份暴露。

**产品含义（需要补的两类素材）**：
现有技术素材库只覆盖了「工艺标准 / 专项方案 / 设备参数 / 实景图」，还缺两类直接影响得分的：
1. **人员与工法**：项目经理/技术负责人履历（脱敏版）、企业工法、专利、QC 成果
2. **体系文件**：质量/环境/职业健康安全三体系文件、检测能力清单

**每条素材要打三个标签**：`可用章节`、`是否含身份信息`（含则入模前脱敏）、`可信度`（用户上传 vs 官方文件）。第二个标签是硬性闸门——企业版工艺标准的内页页眉几乎都印着公司名，直接喂给模型，AI 会原样写进正文，暗标当场废标。

## 七、导出方案

服务端用 `docx` 模板渲染（python-docx 或 docxtpl）：

1. 预置样式模板（标题层级、正文宋体小四、行距 22 磅、页眉页脚、页码）
2. 正文用 Markdown → docx 转换，表格/图片单独处理
3. 自动生成目录域（Word 打开后可更新页码）
4. 暗标模式：清除文档属性（作者、公司）、替换敏感词、移除图片 EXIF

输出：`项目名称-技术标-YYYYMMDD.docx`，存云存储，返回 7 天有效链接。

> 只输出技术标分册。若用户还需要商务标、资格文件、报价表，需自行按招标文件编制——导出页会明确提示这一点，避免用户误以为一份文件就能投标。

## 九、风险与合规

1. **数据安全**：招标文件含商业机密，必须承诺不用于模型训练；存储加密；提供删除入口。
2. **生成内容免责**：明确 AI 产出为"初稿"，需人工复核；不做"保证中标"类表述（竞品的"中标率提升 30%"有合规风险）。
3. **暗标合规**：暗标模式下必须彻底清除身份信息，这是废标高发点，也是我们建立信任的机会。
4. **大模型选型**：优先国产模型（DeepSeek / Qwen / 混元），长文本能力 + 成本可控；解析用便宜模型，生成用强模型。
5. **成本控制**：一份 4 万字技术标约消耗 8—12 万 token，按国产模型价格约 ¥2—5/份，定价 ¥39 有充足毛利。

### 9.1 模型选型：DeepSeek-V4.1-Flash 实测评估（2026-10）

**规格**（官方 API 文档）：上下文 1M、最大输出 384K、默认思考模式、支持 JSON Output / Tool Calls / 图像理解、并发 2500。

**价格**（每百万 token，空闲 / 高峰）：

| 项目 | 空闲 | 高峰 |
|---|---|---|
| 输入（缓存命中） | ¥0.02 | ¥0.04 |
| 输入（未命中） | ¥1 | ¥2 |
| 输出 | ¥4 | ¥8 |

> 高峰为北京时间工作日 9:00—12:00、14:00—18:00；其余时段含周末节假日为半价。投标人夜间赶标恰好落在空闲时段，成本天然更低。

**结论：够做"能交差的初稿"，不够做"能直接投标的终稿"——短板不在模型，在工程。**

强项正好对上技术标的三个痛点：
- **1M 上下文**：200 页招标文件 + 已写章节可一次装入，不必切得过碎，减少跨章前后矛盾
- **384K 输出**：单章一次出 6000 字不需要拼接，文风更连贯
- **JSON Output**：解析阶段的结构化抽取直接用它，不需要额外的解析容错
- **价格**：输出 ¥4/M，是长文生成的关键优势

短板（稀疏 MoE，激活参数小）：
- 深度推理与"严格遵守复杂约束"弱于大模型
- 技术标三大翻车点：**编造规范号/图集号**、**空话套话**、**跨章重复**

**因此不建议单模型干到底，按环节分层：**

| 环节 | 模型策略 | 理由 |
|---|---|---|
| 招标文件解析 → 结构化 JSON | Flash + 非思考模式 + 低温度 | 抽取是"找"不是"想"，便宜且 1M 上下文一次吞完 |
| 大纲规划（评分细则 → 章节树 + 字数分配） | Flash **思考模式**，或换强模型 | 唯一真正"动脑"的环节，结构错则全篇废 |
| 分章生成 | Flash + 强约束 prompt + RAG 素材 | 逐小节循环写，单次 1500—2000 字 |
| 生成后自检 | 规则引擎 + 小模型 | 规范号白名单、暗标扫描、关键词覆盖、字数——不需要大模型 |

**比换模型更有效的四个杠杆**：① 评分细则结构化质量 ② 企业技术素材 RAG ③ 分章策略与上下文管理 ④ 后置自检。这四项做好，Flash 的输出能到"改改就能用"；做不好，换 V4-Pro 也还是空话。

### 9.2 单份成本测算（4 万字技术标）

按 1 汉字 ≈ 0.7 token 估算：

| 环节 | token 量 | 空闲价 | 高峰价 |
|---|---|---|---|
| 解析（招标文件 20—30 万输入，只抽技术标部分） | 输入 ~25 万 | ¥0.25 | ¥0.50 |
| 大纲 + 8 章生成（输出 2.8 万，输入 14 万含 RAG，缓存命中率约 60%） | 输入 14 万 / 输出 2.8 万 | ¥0.17 | ¥0.34 |
| 自检与返修（约 1 次重写） | 输出 ~3 万 | ¥0.12 | ¥0.24 |
| **合计** | | **约 ¥0.55** | **约 ¥1.1** |

开思考模式会让输出 token 翻 2—3 倍，单份约 ¥1—2。**定价 ¥39，毛利率仍在 95% 以上**——成本不是这个产品的约束条件，效果才是。
